## 1. 需要优先处理的问题

### P1：真实接触不一定被捕获，结果依赖接近方向

位置：`Pool/Assets/Scripts/Inventory/InventoryRunFlow.cs:35–39`。捕获只判断两刚体中心距离 `< 0.5`，没有使用碰撞接触/实际抓捕范围。玩家胶囊碰撞体大小 `0.4 × 0.55`，中心向下偏移 `0.18`；怪物圆形碰撞体随对象缩放后的纵向半径约为 `0.2781`。

在独立运行的构建副本中，保留原场景碰撞体，将玩家固定在 `(2,-1)`，用无动作敌人状态排除 AI 改速度的影响，然后令怪物从上下两方向以速度 4 接近。关闭初始捕获保护，并直接执行当前 `Flow.Tick`：

| 接近方向 | 停止时中心距离 | 碰撞体间距 | 是否捕获 |
|---|---:|---:|---|
| 下方 `(2,-2.3)` 向上 | 0.7281 | -0.0050（接触求解容差） | 否 |
| 上方 `(2,0.3)` 向下 | 0.3675 | -0.0056（接触求解容差） | 是 |

玩家刚体在夹具中临时设为 Kinematic，避免被推动；未改两者碰撞体或捕获判定。结果说明中心阈值与实际接触边界不一致，普通有碰撞的追击可在玩家下方被碰撞体挡住，却不进入捕获流程。现有完整回归通过“直接把怪物放到玩家中心”检查捕获，不能覆盖这种问题。

建议：采用专门的抓捕触发范围或实际接触判定；明确哀区穿障时抓捕范围是否穿墙；新增上下左右接近、玩家奔跑/冲锋、三秒保护结束和高速经过的集成测试。

### P1：删除出口引用仍能通过构建配置校验，完成任务也无法结算

位置：`InventoryConfiguration.cs:9–35`、`InventoryRunFlow.cs:30–33`、`Editor/BackpackInstaller.cs:184–192`。

复现：保留当前全部交互物和两组有效目标，仅设 `bag.exit = null`。实际 `InventoryConfiguration.Validate` 返回空错误字符串、`configured = true`，普通构建校验使用同一方法，仍会接受。通关逻辑又要求 `bag.exit != null`，因此所有目标达成也无法进入结算。

建议：对当前 Demo 的通关出口进行必需引用校验，并按场景使用范围补齐门碰撞体、视图、UI 必需字段、模板和 EventSystem 检查；区分允许不带怪物的测试场景与正式演示场景。正半径、正冲锋速度和非负计时参数也尚未校验，应一起明确范围。

当前 `SampleScene` 出口引用存在；这是换场景或编辑器误删时会发生的缺口，不代表现有场景已经缺出口。

### P2：玩家区域和怪物行为读取不同坐标，完整回归本次未通过

位置：`BackpackController.cs:29–30`、`Enemy.cs:30–31,59–62`、`BackpackPlayChecks.cs:90–91`。

背包的玩家区域从 `Rigidbody2D.position` 查询；怪物选择电闸/玩家以及三倍追击速度，从目标 `Transform.position` 查询。玩家刚体启用了插值，物理位置与显示 Transform 在传送或跨边界时可能不是同一时刻的位置。

隔离夹具实际记录到：玩家刚体 `(2,-1)`、背包区域 `Anger`，玩家 Transform 仍为 `(-2,0)`；怪物在哀区、穿障开启，但读取的追击速度是 `1.6`，而玩家已出哀区时应为 `12`。夹具禁用了玩家正常更新并执行传送，用于证明两套坐标读取可能产生不同结果；不能据此声称正常玩法一直保持错误速度。

原 v1.3.1 试玩包用 `-inventory-check` 连续运行两次，均在“怪物仍在哀区、玩家进入怒区时三倍穿障”这一检查失败。尚未把整个失败完全归因于正常玩法；测试的直接传送、渲染/物理同步和输入时序仍需要独立处理。增加失败日志的构建副本又在首球输入检查失败，进一步说明该回归对执行时序也不够稳健。

建议：玩家与怪物规则统一读取物理位置；传送夹具显式等待固定步并记录身体/显示坐标、双方区域和实际速度。重新从当前源码构建，再重跑完整流程。不能用旧的 `INVENTORY_PLAY_PASS` 记录覆盖这次失败。

### P2：非必需任务物的详情仍宣称“自动计入本关收集目标”

位置：`BackpackView.cs:97`、`BackpackPresentation.cs:156–163`；实际目标统计在 `InventoryRunFlow.cs:15–18`。

复现：从 `requiredTaskIds` 移除铜片，但保留交互物和另外三个任务目标；收集铜片后进入暂停详情。配置依然合法，铜片会占任务格，开门计数不包含铜片；实际详情仍显示“自动计入本关收集目标”。

建议：必需任务物显示“计入出口目标”，可选物显示“已收集，本关出口不要求该物品”；容量、携带数和门目标数保持独立。当前四任务物全必需的场景不会暴露该错误，扩展可选物时会出现。

## 2. 集成前需明确的边界

| 项目 | 当前情况及建议 |
|---|---|
| 已拾取物品的可变引用 | `BackpackData` 保存原 `InventoryItem` 对象，但 ID 索引保留收集时字符串。实际夹具把已收集球 ID 从 `original` 改为 `changed` 后，装备显示新 ID、索引仍只有旧 ID，还可再次收集同一对象形成两个槽。关卡作者须保持 ID/类别稳定；若需要运行时编辑，应复制记录或阻止变更 |
| 清空数据与世界复位 | `Data.Clear()` 只清背包，不重置交互物的 `Completed` 或隐藏状态。正式重开使用场景重载，其他系统不要拿 `Clear()` 替代重开；未来无重载重试必须补完整世界复位入口 |
| 更多光球 | 当前四格没有丢弃/替换，当前场景只有四球。若扩展为五球以上，应先决定满栏替换/丢弃规则与必要能力可达性，不直接增加必须使用的球 |
| 冲锋终止 | 当前按设计一直冲到障碍，没有最长距离/时间或取消键。现有封闭演示地图支持该行为；地图扩大、开放边界或障碍层误配置后，需要脱困机制和配置检查 |
| 电闸标记 | 透视会显示登记的电闸，不区分完成/未完成，最多 32 个标记。至少应在文案或样式上区分状态；增加目标后检查标记上限与避让 |
| 哀区观察 | 五单位距离 + 35° 夹角 + 射线是近似感知，没有直接复用手电遮罩。需实机对照“玩家实际看得到”与威胁提示是否一致 |
| 捕获后的体力与其他关卡系统 | 背包恢复会清技能冷却但不补满体力，也不统一重置其他关卡状态。这属于当前 Demo 行为；正式失败规则确定后一起更新实现、提示和验收 |
| 单类型门目标 | 当前任务和电闸两组必须都非空。只收集/只拉闸关卡需明确是否要支持，不能把空数组解释为自动完成 |

存档、跨场景携带、消耗品、喜/惧新能力以及拖拽排序不在当前背包范围内，属于后续需求；本次没有将它们算作当前功能缺陷。

## 4. 推荐修复与验收顺序

1. 修捕获范围：四向实接触一致触发，保护期有效，高速穿越不漏判。
2. 修关键配置校验：删除出口必须阻止正式演示场景构建；补 UI 引用和数值范围检查。
3. 统一区域坐标并稳定完整回归：按固定步传送与断言，记录失败上下文，当前源码新构建必须走完收集、融合、捕获、通关、重开。
4. 修任务物详情口径：新增一个可选物，确认携带量增加而门目标不增加，详情准确区分。
5. 先确定正式失败/光球经济规则，再增加存档、替换或更多能力；安排至少三名未读文档玩家测试追逐中的操作与理解。
