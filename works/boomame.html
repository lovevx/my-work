Boomame · 2D 挂机破坏游戏

个人独立项目 · Godot 4.7 · 一人完成玩法→数值→开发→迭代完整闭环

Boomame 是什么：一款 2D 休闲「破坏 + 挂机」游戏——玩家用锤子砸楼赚金币，通过升级逐步解锁自动轰炸炮台，从「手动破坏」平滑过渡到「自动化挂机」，越玩越省力。

为什么做它：它是我为求职打造的完整闭环代表作。我不是只写代码的人，也不是只会写文档的人——Boomame 让我一个人把玩法设计 → 数值平衡 → Godot 开发落地 → 试玩迭代整条链路走通，并把每一步沉淀成可讲清楚的设计文档，作为"我有能力从 0 到 1 独立把一个系统的设想变成立得住的产品"的证物。

一、项目概览

Boomame（炸弹 + 玩家的组合词，"拜姆"）是一个约 2 个月内的个人独立项目，基于 Godot 4.7（GL Compatibility + Jolt 物理）开发的 2D 桌面端游戏。当前是一个可玩的垂直切片（vertical slice）：核心循环完整可跑通，转生 / 永久技能树 / 存档系统已全链路实装。

  • 一句话定位：手动砸楼赚金币 → 升级 → 解锁自动轰炸炮台 → 自动化替代手动 → 越玩越省力。
  • 目标体验关键词：干脆（放置即响应、爆炸即摧毁）、爽（震屏 + 碎屑飞散 + 碎裂层层叠加）、变强感（升级后立刻感知到范围/伤害/金币变化）、省力（自动化炮台逐步替代手动点击）。
  • 关键时刻：First 30s（30 秒内跑通「锤砸→赚金币→升级→解锁炮台→自动轰炸」闭环）；首炸（第一颗炸弹同时给出震屏 + 方块飞散 + 碎裂，建立破坏爽感的第一印象）。
  • 工程规模：10+ 独立模块、12 张真实方块材质贴图、33 帧炮台待机动画、双 BGM 轮播、360 个物理方块；场景切换做了分帧实例化等性能优化。

二、玩法与核心循环

Boomame 的核心是一句贯串始终的设计主张：破坏方式的成长 = 从手动逐步滑向自动化。游戏不按"数值越堆越大"的老路子走，而是把成长做在"破坏方式本身的进化"上。

  • 动作循环：破坏 → 收益 → 投入升级 → 更强破坏。
  • 机制循环（核心）：手动（锤）→ 半自动（炮台辅助）→ 全自动（多炮台轰炸）。
  • 锤子前期是唯一手段：高频点击破坏，锤子承担核心作用。
  • 炮台中期登场：通过机制型升级项解锁第一台自动炮台，炮台自动瞄准 / 抛射 / 爆炸，实现更大范围破坏，锤子开始退居辅助。
  • 后期全自动：更多 / 更快 / 更强炮台逐步替代手动，玩家"越砸越累"走向"越玩越省力"。
为什么把"省力"做成成长本身：传统放置游戏的核心反馈是数值变大的爽感；Boomame 更进一步——把自动化这个机制当成升级的长期价值。升级的意义不只是"数字更大"，而是"重复手动操作被更强的自动化机制替换"。因此「省力 / 挂机变强」本身就是成长反馈的一部分，形成区别于纯 DPS 堆叠的成长曲线。

同时，破坏反馈全项目统一为「粉碎 / 碎屑飞溅」（不做掉落物品），保证破坏手感的一致性——菱形原则：反馈只看"碎得多爽"，不看"掉了什么"。这是我在体验设计上刻意立起来的一条纪律。

三、数值模型（重点）：单局加法 × 转生百分比，双层结构

数值是挂机游戏的骨架，也是我最想重点讲的设计点。Boomame 采用双层数值成长模型，并敲定了一条核心公式原则：同层同类用加法累加、跨层用乘法叠加，乘法层数固定为两层，杜绝无限叠乘失控。

最终值 =（基础值 + 单局加法层）×（1 + 转生百分比层）

上层是单局加法：锤子伤害每级 +0.3、锤子速度 +0.4、金币倍率 +0.5……以线性加法为主，每局结束后归零，给"本局变强"的即时反馈（代表未来的"线性爽感"）。

下层是转生永久百分比：用转生点 RP 点亮永久技能树，如"破坏之力 +5%/+10%/+15%"、"金币之心 +50%/+100%/+150%"等，以乘法为主，跨局永久保留（代表"指数累积"）。

两层相乘，同时保证"每个属性都能成长"与"长线平衡、避免膨胀"。

为什么单局用加法、转生用百分比，而不把两者的倍率在两处都乘上？因为同样的倍率两处相乘会指数爆炸。假设锤子伤害既在单局加"翻倍"又叠加转生"翻倍"，两个乘法叠一起是 2×2=4 倍，多刷几轮后数值彻底失控。所以 Boomame 让单局层线性（加法）、转生层指数（乘法）、两层相乘，乘法层数锁死为 2，指数被控制在单层内。

1. 用 sqrt 做边际递减，防止数值无限膨胀

转生点收益是"深转收益高、浅转收益低"，但收益曲线必须边际递减，否则玩家无限刷单局就能无限变强。转生点（RP）采用 sqrt 类曲线公式：

gain_rp = floor( RP_GAIN_K × sqrt( run_total_gold / RP_GAIN_BASE ) )
当前生效参数：RP_GAIN_K = 1.0、RP_GAIN_BASE = 300 000、低于 MIN_RUN_GOLD_FOR_GAIN = 10 000 得 0 RP（不奖励浅转）。
收益参考：单局累计 30 万金币 → 1 RP；120 万 → 2 RP；270 万 → 3 RP；750 万 → 5 RP；3000 万 → 10 RP。

sqrt 曲线的特性是：金币每翻数倍，RP 收益只以开方级增长（1→2→3→5→10），越往后想再拿一个 RP 需要投入成倍的积累。这既保留了"深转变强"的长期目标，又天然压制了"无限速刷"的膨胀路径——是双曲线里最简单却最有效的约束之一。

2. 平衡基准是 TTK（击破时间），而不是纯 DPS

挂机游戏常犯的错是拿"DPS × 时间"当平衡单位。Boomame 有三大机制让通用 DPS 公式失效：点击 CD（节拍器）决定了玩家输出有硬频率上限、多方块分挡把血量与金币做成"分挡换皮"而非线性上涨、击破才掉金币让收入按"击破次数"结算。因此本作的平衡基准是 TTK（击破一次所需时间），升级的本质是"压缩 TTK"而非"调大 DPS"。

  • 点击 CD：基础 0.5s（Hammer.attack_speed=2.0），并设下限 MIN_COOLDOWN = 0.30s——CD 一旦趋近 0，多方块挡位分层会完全失效、退化为纯数值碾压，CD 下限是挡位设计的"守卫"。
  • 方块挡位：墙 / 窗 / 楼板 × 4 挡，由累计摧毁数（40 / 120 / 300）驱动，更硬同时更值钱（升挡是正向奖励），代替"每块线性涨血"。
  • 理想 TTK ≈ CD ×（1.5 ~ 3）：这是节奏平衡标尺，甜点区允许偶尔失误又紧凑，超 5× 则提示升级或拉自动。
  • 30 分钟单局节奏锚点：第 5–8 分钟解锁第一台炮台、第 18 分钟进入首次转生窗口（1–2 RP）——所有参数都围绕这条"点击→自动化"两阶段的时间线标定。

四、技术实现

1. 无限层物理级联破坏

建筑是一栋无限层物理塔，按列托管（12 列 × 每列 30 块可见 = 360 个物理方块），方块默认为冻结的独立刚体。核心机制是：

  • 任一方块被砸碎 → 该列上方失去支撑的方块各自作为独立刚体真实下落（物理级联，而非整层一起塌平）。
  • 落到底部存活块 / 地面后 → 吸附回网格并重新冻结。
  • 自动补层 → 当某一列没有方块在下落时，自动在楼顶补出新层，任意列始终维持满高，形成无限塔。
迭代取舍（真实过程）：最早版本做的是"整层整体下坠 + 收拢偏移"，但发现破坏缺层次、掩盖反馈，且整层逻辑复杂易出 bug。改版后用"每列物理级联 + 自动补层"，并以"扫描该列是否仍有方块在下落"来判断补层时机，而非计数器——这对"一列内多块同次摧毁、下落中被额外摧毁"等重叠情况更稳。这是一次"用更接近物理直觉的数据结构，换掉笨重状态机"的取舍。

2. 分帧实例化：化解切场主线程卡顿

进入场景时原本要一次性实例化 360 个 RigidBody2D 并配置物理，结果从主菜单切进游戏时主线程冻结约几百毫秒。改造方案是分帧实例化：每帧只生成 24 块、共 15 批，且自下而上生成——保证地面支撑与塌陷目标尽早可用。

  • 定位：切场卡顿来自一次性同步生成 360 个物理方块，阻塞了主线程。
  • 处理：改为每帧 24 块 × 15 批的分帧实例化，自下而上铺楼。
  • 结果：彻底消除切场冻结——顺带证明"性能不只是一个引擎话题，也会直接影响玩家首次体验的顺滑感"。
另一条工程纪律——物理回调时机：炸弹爆炸回调里若同步 add_child() 新刚体或改动 freeze，会触发引擎 flush 阶段报错（body_set_shape_disabled）。Boomame 把"重建 / 压实 / 补层"统一 call_deferred() 推迟到物理步结束后执行，稳定不再报错，也让"改动物理状态前先想清楚时机"变成了固定的工程习惯。

五、数值与文档工程化

个人项目最容易烂掉的地方是"数值越调越乱、越堆越多"。Boomame 用两件套把数值管起来，让它可调、可查、可回归：

  • @export 统一暴露参数：所有可调数值都通过脚本顶部 @export 暴露，禁止在函数体内散落硬编码 magic number——想调一处手感，去脚本顶部改一个常量即可。
  • 规格文档（SPEC）双向同步：SPEC.md 维护完整的数值边界表（点击 CD、方块血量分档、转生阈值、爆炸参数…），与脚本 @export 一一对应，保证"设计参数 ↔ 工程常量"双向同步。改数值先看 SPEC 定锚点，改完回填测试记录。
  • 白模验证而非拍脑袋：手感 / 经济敏感参数（点击 CD、转生基准）不直接改，先在 SPEC / EXPERIENCE 定节奏锚点（挡 0 TTK 甜区、锤速 Lv2 后 CD 是否触及下限贬值），再动引擎常量，最后回填实测结论——建立"设计预期 → 改参 → 实测回填"的闭环（2026-08-25 实践）。
  • 近 20 篇设计文档：沉淀了完整 GDD、数值平衡、成长模型、转生、技能树、材质分档、体验与测试记录、模块分工、AI 提效工作流、竞品拆解等近 20 篇文档，把每一次设计决策和迭代过程都留档可回溯。
文档即背书：这些文档不是摆设，而是"我能在面试里把设计到落地讲清楚"的依据——每个核心章节都附"设计决策 + 迭代过程"手记，例如"为何不用手动放炸弹而走自动挂机""为何单局加法 × 转生百分比而非两层乘法"。面试官可以直接追问任何一个子系统，因为每个决策都有当时的理由沉淀在文档里。

六、从 0 到 1 的迭代思路

整个项目是一个约 2 个月的个人作品，主线是先验证最简闭环 → 再补内容与背书 → 稳定与发布 → 求职打磨。核心方法论是"先让一个最小循环立起来，再一点点加"：

  • 阶段 0 立项：拆解同品类 What the Buck?!，只学其设计方法、自行压缩数值，确立"挂机破坏"与自动挂机方向。
  • 阶段 1 MVP 验证：搭建 Godot 工程，跑通最简闭环（核心循环 + 物理破坏 + 金币 + 升级骨架）；完成"整体下坠 → 每列物理级联"的关键迭代。
  • 阶段 2 体验验证：让 First 30s 成立，破坏反馈统一为"粉碎"，确立"干脆 / 爽 / 变强 / 省力"四个体验关键词。
  • 阶段 3 内容资产：补真实材质 + 三挡质感 shader、炮台 / 炮弹美术、尘土特效、双 BGM、转生全链路、屏幕转场。
  • 阶段 4 稳定发布：分帧实例化切场优化、物理回调修复，导出 Windows + Android 版本。
  • 阶段 5 求职打磨：提炼 PORTFOLIO 材料、补生涯统计，面向求职收尾。
一个问题驱动式的迭代观：这个从 0 到 1 的过程里，我反复验证的不只是"能不能跑"，而是"体验成不成立"。MVP 阶段我盯一个指标——玩家能不能在 30 秒内自发跑通核心闭环并感到变强；每加一个系统，都会先问"它让循环更畅快，还是让机制打架"。宁可按规划砍掉没验证的长线功能（如离线收益），也要保证"闭环完整 + 体面收尾"。
